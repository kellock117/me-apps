# SDD (Spec-Driven Development): 스펙 먼저 개발하기

이 프로젝트에서 **동작이 바뀌는 변경**을 만드는 방식입니다. 코드를 쓰기 전에 "무엇을, 왜, 어떻게 확인할지"를 먼저 정하고, 구현은 그 약속을 따릅니다.

## 왜 하나

- **모호한 요구를 코드에서 풀면 비쌉니다.** 질문으로 먼저 풀면 싸게 끝납니다. (고객의 모호한 문제를 받아 범위를 정하는 일을 연습하는 자리이기도 합니다.)
- **AI가 구현할 때 기준이 필요합니다.** 스펙이 없으면 "그럴듯한" 코드가 나오고, 있으면 완료 기준으로 맞는지 대조할 수 있습니다.
- **추적이 됩니다.** 요구 → 스펙 → 티켓 → PR → 테스트가 이슈 번호로 이어집니다. 나중에 "왜 이렇게 만들었나"를 찾을 수 있습니다.

## 언제 쓰나

| 구분 | 변경 | 방식 |
| --- | --- | --- |
| **강제** | 새 기능, 동작이 바뀌는 변경(화면 흐름, 규칙, 데이터 구조, 권한) | 아래 전체 흐름 |
| **예외** | 오타·문구 수정, 문서만 바뀌는 일, 운영 장애 핫픽스 | 스펙 없이 진행하고 끝난 뒤 `NOTES.md` 또는 PR에 한 줄 기록 |

경계가 애매하면 사용자에게 묻습니다. 형식이 목적이 되지 않도록, 작은 변경까지 강제하지 않습니다.

## 전체 흐름

```
 1. 한 줄 요구
      ↓
 2. 그릴링 (/grill-me)            ← 모호함·모순·빠진 경우를 캐묻기
      ↓   결정이 남으면 /grill-with-docs → ADR·용어집
 3. 스펙 (/to-spec)               ← GitHub 이슈로 게시 · 테스트 지점 합의
      ↓
 4. 티켓 (/to-tickets)            ← 얇은 수직 조각 + 차단 관계
      ↓
 5. 구현 (/implement)             ← 테스트 먼저(TDD) → 코드 → 리뷰 → 커밋
      ↓
 6. 검증·PR                       ← 완료 기준 대조, `pnpm check`, `Closes #번호`
      ↓
 7. 회고 (/retro)                 ← 환경을 고칠 점 찾기
```

사람이 승인해야 다음으로 넘어가는 지점은 **2→3(질문에 답하고 범위 확정), 3(테스트 지점 합의), 4(티켓 쪼개기 확인), 6(커밋·푸시)** 입니다.

> 괄호 안은 Claude Code 스킬 이름입니다. 스킬은 작성자의 로컬 환경(`~/.claude/skills/`)에 있어서 이 레포에는 들어 있지 않습니다. 레포를 보는 사람은 각 단계의 목적과 산출물만 읽으면 됩니다.

## 단계별 설명

### 1. 한 줄 요구
- **입력**: 하고 싶은 것을 한 문장으로. 예) "모임 전날 멤버에게 알려 주고 싶다."
- **산출물**: 없음(대화).
- **끝난 기준**: 한 문장으로 말할 수 있다.

### 2. 그릴링 (`/grill-me`)
- **무엇**: AI가 계획의 빈틈을 집요하게 질문합니다. 누가, 언제, 실패하면 어떻게 되는지, 하지 않을 것은 무엇인지 등입니다.
- **원칙**: 질문은 한 번에 하나씩 하고, 답이 모호하거나 앞과 모순되면 다시 묻습니다. 답이 없는 것은 "미정"으로 남깁니다. 코드부터 보고 알 수 있는 건 코드를 보고 답하지, 사용자에게 묻지 않습니다.
- **`/grill-with-docs`**: 같은 인터뷰를 하면서 결정이 나오면 **ADR**(`docs/adr/`)과 **용어집**(`GLOSSARY.md`)에 바로 기록합니다. 이후 스펙과 테스트가 같은 용어를 씁니다.
- **산출물**: 범위가 정리된 대화, 필요하면 ADR·용어집.
- **끝난 기준**: 남은 "미정"이 구현을 막지 않는 수준이다.

### 3. 스펙 (`/to-spec`)
- **무엇**: 앞선 대화를 스펙으로 정리해 **GitHub 이슈**로 올립니다. 새로 인터뷰하지 않고, 이미 나온 것을 종합합니다. 코드베이스를 먼저 읽어서 기존 용어와 ADR을 따릅니다.
- **테스트 지점(seam) 합의**: 어디에서 동작을 확인할지 먼저 정해 사용자와 확인합니다. 가능하면 기존 지점을 쓰고, 가장 높은 지점 하나로 줄입니다.
- **스펙 구성**:
  1. 문제(사용자 입장에서)
  2. 해결(사용자 입장에서)
  3. 사용자 스토리(많이, "~로서 ~하고 싶다, 그래서 ~")
  4. 구현 결정(모듈, 인터페이스, 스키마, 계약. 파일 경로와 코드는 쓰지 않음)
  5. 테스트 결정(무엇을, 어디서, 선례)
  6. 범위 밖
  7. 추가 메모
- **산출물**: GitHub 이슈 1개(`ready-for-agent` 라벨).
- **끝난 기준**: 사용자가 스펙을 승인했고, 완료 여부를 문장으로 판정할 수 있다.
- **주의**: 레포가 공개이므로 이슈에 실명, 키, 개인 기록을 쓰지 않습니다.

### 4. 티켓 (`/to-tickets`)
- **무엇**: 스펙을 **얇은 수직 조각(tracer bullet)** 으로 쪼갭니다. 한 조각이 스키마, 서버, 화면, 테스트까지 좁지만 끝까지 이어지는 길이라서, 끝나면 혼자서도 확인·시연이 됩니다. 층별(DB만, 화면만)로 나누지 않습니다.
- **차단 관계**: 각 티켓이 어떤 티켓이 끝나야 시작되는지 적습니다. 막힘이 없는 티켓이 "지금 할 수 있는 것(frontier)"입니다.
- **확인**: 크기가 알맞은지, 차단 관계가 맞는지 사용자에게 묻고 고친 뒤 게시합니다.
- **산출물**: 스펙 이슈에 달린 하위 티켓들(GitHub의 sub-issue와 blocked-by).
- **끝난 기준**: 조각마다 완료 기준이 있고, 하나가 한 번의 작업 맥락에 들어간다.

### 5. 구현 (`/implement`, 큰 스펙은 `/implement-spec`)
- **TDD**: 합의한 테스트 지점에서만 테스트를 쓰고, 실패(red) → 통과(green)를 반복합니다. 구현 세부가 아니라 **외부에서 보이는 동작**을 확인합니다.
- **스펙이 틀렸다면**: 코드를 고치기 전에 **스펙을 먼저 고치고** 사용자에게 알립니다.
- **스펙에 없는 것은 만들지 않습니다.**
- **끝나면**: 코드 리뷰(`code-review`)를 돌리고 지적 사항을 고친 뒤 커밋합니다.
- `/implement-spec`은 티켓마다 새 하위 에이전트를 별도 작업 폴더에서 돌리고, 통합 브랜치에서 합칩니다. 티켓이 많고 서로 독립일 때 씁니다.

### 6. 검증과 PR
- **완료 기준 대조**: 스펙의 기준을 하나씩 확인한 결과를 보여 주고 멈춥니다. 미달이면 알립니다.
- **자동 검사**: `pnpm check`(타입, 테스트, 빌드) 통과.
- **PR**: 본문에 `Closes #스펙번호`를 달아 머지되면 이슈가 닫히게 합니다.
- **끝난 기준**: 완료 기준 전부 통과, CI 통과, 사용자의 머지 승인.

### 7. 회고 (`/retro`)
- **무엇**: 끝난 세션을 돌아보며 **다음에 더 잘 돌게 할 환경 개선**을 찾습니다. 파일을 찾는 데 오래 걸린 곳, 자동 검사로 막을 수 있던 실수, 규칙 보강 등입니다.
- **산출물**: CLAUDE.md, 테스트, 문서의 개선 제안.
- **결정은 ADR로**: 스펙이 닫히면 그 과정에서 내린 결정을 `docs/adr/`에 남깁니다.
- **기능 문서 갱신**: 기능이 끝나면 무슨 기능인지, 어떻게 동작하는지, 특이사항을 `docs/features/<기능>.md`에 정리합니다. 개발 문서의 원본은 레포 한 곳이고, 노션 개발자 위키는 쓰지 않습니다. (폐기 2026-11-17: 예전의 "노션 위키 갱신" 단계는 이 단계로 대체됨)

## 저장 위치

| 무엇 | 어디 |
| --- | --- |
| 스펙, 티켓 | GitHub 이슈 (`docs/agents/issue-tracker.md`) |
| 결정 기록(ADR) | `docs/adr/` |
| 용어집 | 루트 `GLOSSARY.md` |
| 개인이 할 일 | `docs/TODO.md` → 끝나면 `docs/DONE.md` |
| 동작 특이사항·함정 | `docs/NOTES.md` |

## 지켜야 할 것

1. 동작이 바뀌는 변경은 **스펙이 승인되기 전에 코드를 쓰지 않습니다.**
2. 스펙이 없는 채로 요청이 오면 AI는 구현하지 않고 `/grill-me` 실행을 먼저 안내합니다. (이 스킬들은 사용자가 직접 실행해야 합니다.)
3. 한 번에 작업 단위 하나만 진행하고, 단위가 끝나면 완료 기준 대조 결과를 보여 준 뒤 멈춥니다.
4. 스펙과 구현이 어긋나면 스펙을 먼저 고칩니다.
